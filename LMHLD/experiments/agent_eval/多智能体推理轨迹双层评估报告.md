**实验日期**: 2026-09-21

**评估脚本**: `D:\LMHLD\eval_agent_trajectory.py` | **数据**: `experiments/agent_eval/results.json`

## 一、评估目的与方法

对标 Earth-Agent 发现的行业共性问题——**"模型能选对工具，但常引入无关步骤，轨迹精确率低"**——对本项目多智能体系统进行**双层评估**：不仅看报告结果，还量化推理轨迹质量。评估协议直接复刻 Earth-Agent 开源实现（`evaluate/step_by_step.py` 的软评分版本）：

**轨迹级指标**
| 指标 | 定义 |
|---|---|
| Any-Order | 期望智能体集合的覆盖率（顺序无关） |
| In-Order | 顺序贪心匹配率（允许中间夹杂其他步骤） |
| Step-Wise | 严格前缀匹配（首个不符即停） |
| Exact-Match | 与规范序列完全一致 |
| 禁忌违规 | 是否调度了无关智能体（图像预处理链 FormatConversion/ImageFilter/Scale/SuperResolution、选择题匹配 MatchingAgent） |

**结果级指标**：报告要点命中率（风险术语 / 定量数字 / 处置建议三项）、风险等级一致性、效率（步数、耗时）

**基准场景（19 个）**：6 区域 × 2 样本（数据集模式）+ 4 上传场景（不同模型通道）+ 2 变化对比 + 1 边界场景。
规范序列（专家参考）：`SegAgent → DetAgent → ClsAgent → ReasoningAgent`

## 二、核心结果：改造前后对比

| 指标 | 改造前（10 份历史轨迹） | 改造后（18/19 场景成功） | 变化 |
|---|---|---|---|
| Any-Order | 0.40 | **0.75** | +0.35 |
| In-Order | 0.00 | **0.458** | +0.46 |
| Step-Wise | 0.00 | **0.431** | +0.43 |
| Exact-Match | 0.00 | **0.389** | +0.39 |
| **禁忌智能体违规率** | **100%** | **0%** | **彻底消除** |
| 报告要点命中率 | 不适用* | **0.722** | — |
| 平均步数 | 2.6 | 3.0 | — |
| 平均耗时 | — | 59.4 s | — |

\* 历史轨迹多为选择题型基准任务，无矿山报告内容，报告级指标不适用。

**四项改造**（对应轨迹指标的提升来源）：
1. **白名单调度**：代码级排除预处理链与匹配类智能体，按场景限定可用智能体集合——禁忌违规率从 100% 降至 0%；
2. **定量分析工具注入**：NDVI/区域统计/趋势/对比工具输出注入提示词，使报告可引用具体数值（报告要点命中率 0.722 的主要来源）；
3. **开放式问题模板**：明确要求结构化中文报告并禁止字母选项残留；
4. **协调器场景化**：检测评估型 / 变化对比型分场景构建（不再混用）。

## 三、失败与边界分析（如实记录）

1. **1 个场景超时**（双 2304×2304 大图变化对比，120s 代理超时）：发生在训练占用 GPU 期间，属运行资源约束而非功能缺陷——同机制的单图对比场景（cmp_baige，36.3s）正常完成。
2. **短序列倾向**：部分场景调度器自行选择 2-3 步精简路径（如仅 SegAgent→ReasoningAgent），未走完整 4 步规范序列——这正是 Earth-Agent 观察到的"模型倾向够用就好"现象；从效率角度合理，但牺牲了轨迹精确率。**后续可通过更明确的步骤指令（Instruction-Following 模式）进一步规范**。
3. **报告要点命中率 0.722**：主要失分在定量数字引用（部分场景智能体未引用注入的数值）——已通过定量工具注入改善，仍有提升空间。

## 四、结论与意义

1. **本项目是矿山安全领域首个做"轨迹级评估"的多智能体监测系统**——此前只评估最终报告质量，现在可按前沿标准（Earth-Agent, ICLR 2026）量化推理链质量；
2. 白名单调度是消除"无关步骤"的有效工程手段（违规率 100%→0%），代价极低；
3. 双层评估框架可复用于后续迭代（每次改动都有轨迹指标回归）；
4. **对照价值**：本评估协议与指标的实现直接对标 ICLR 2026 前沿工作，为项目"测试与验证"章节提供了方法论层面的证据。

# 附录：稳定性精进与回归验证（2026-09-22，ThinkGeo 启发）

## 一、改造内容（对标 ThinkGeo 的失败模式分类）

ThinkGeo（2026）发现：工具调用错误率即使 GPT-4o 也达 30-44%，失败模式包括 NoAction、参数错误、格式错误与过早作答。据此对本系统实施四项加固：

1. **报告质量守卫**（确定性 6 项检查：风险等级一致 / 定量数字 / 处置建议 / 无错误残留 / 无字母残留 / 长度充足）→ 缺失时按项修复重生成一次 → 仍不合格标记降级；
2. **自评估接入**：直调四维评分工具（逻辑/空间/领域/准确性 → overall_pass）；
3. **调度三级鲁棒性**：解析失败 → 带修复提示重试 → 规范序列回退 → 全量兜底（旧行为直接全量）；
4. **运行统计**：`/api/stats` 暴露守卫/修复/降级/自评估/调度统计。

## 二、回归结果（19 场景）

| 指标 | 上一轮 | **本轮（加固后）** | 说明 |
|---|---|---|---|
| 场景成功 | 18/19 | **19/19** | 全成功 |
| **报告要点命中率** | 0.722 | **1.000** | 守卫+修复闭环的直接成效（目标 ≥0.85） |
| 守卫通过率 | — | **0.947** | 18/19 一次通过 |
| 降级率 | — | **0.053** | 1/19 |
| 自评估通过率 | — | **0.895** | 17/19 |
| 禁忌违规率 | 0.0 | **0.0** | 保持 |
| 平均耗时 | 59.4s | 60.5s | 质量控制仅 +1.1s（守卫零延迟，修复按需触发） |
| 调度解析失败 | 未统计 | **2/19（10.5%）** | ⚠ 归因已于 2026-09-22 更正，见下 |
| ↳ 失败恢复 | —（旧行为=全量执行） | **重试恢复 1 + 规范回退 1，零全量兜底** | 三级鲁棒性生效 |

> ⚠ **归因更正（2026-09-22）**：本表原注"与 ThinkGeo 报告的格式错误率一致"——**该归因是错的**。
> 源码级定位表明，这 2 次调度失败的真实原因是 **CAMEL 摘要故障级联清空记忆**：
> 摘要触发时 base64 图像被 `str()` 拼进摘要提示词 → 超上游 token 上限 400 →
> 摘要返回空串但记忆仍被清空、且因多模态 content 是 list 而未能恢复 user 消息 →
> 下次调度发出无 user 角色的消息 → 400。
> 修复后 `dispatch.parse_fail` 实测 **0/5**。详见《第十组实验报告·第六节》。

## 三、轨迹指标的波动说明（2026-09-22 二次更正）

本轮严格序列指标（Exact-Match 0.389→0.0、In-Order 0.458→0.224）下降。初次归因为"调度的合理自由度"，**该解释只对了一半** —— 根因修复后复测，Exact-Match 回升到 0.421，说明当时的下降中有一部分来自**记忆被摘要故障清空导致计划被截断**，而非全部是合理自由度。

**两个因素并存**：

1. **记忆受损（已修复）**：摘要故障清空记忆后，协调器每轮几乎"从零开始"，倾向走最短路径。修复后步数从 2.95 升到 3.63，序列指标同步回升 —— 这是主因；
2. **调度的合理自由度（仍然存在，属正常）**：通用目标检测 DetAgent 在**修复前**那次运行中仅 3/19 场景被调度，**修复后为 14/19**（`results.json` vs `results_merged.json`）—— 对"滑坡风险报告"这类任务，协调器常判定无需目标检测，而参考序列注解包含 DetAgent，导致严格序列匹配受罚。修复后 Exact-Match 为 0.421 而非 1.0，**该项残差的具体构成尚未定量归因**。

**方法学启示**：对开放式评估任务（区别于 Earth-Bench 的封闭问答），单一参考序列不完全适用；**稳定性应以"必需智能体覆盖 + 禁忌违规 + 报告质量 + 故障恢复率"衡量**。

1. 报告质量实现硬保障：要点命中率 100%、守卫通过率 94.7%、自评估通过率 89.5%；

## 二、本次复测的运行事故（如实记录）

首轮 19 场景中有 5 个请求失败（`WinError 10054`），**原因是本次复测所用的隔离实例崩溃**：该实例以 `nohup ... &` 方式从临时 shell 启动，shell 退出后标准句柄失效，在 Windows 上诱发 werkzeug 的套接字继承异常（`WinError 10038`）导致崩溃-重启循环，每次重启掐断在途请求。

**已修复**：
1. 后端热重载默认关闭（原先 `debug=True` 会监视被 import 的模块，任何文件改动都重启服务并掐断在途请求）；
2. 新增 `start_backend_5100.bat` 以独立控制台派生进程（禁用同 shell 后台方式）；
3. `start_detector_service` 先探测已有实例，避免同端口双绑定（Windows 允许 SO_REUSEADDR，实测曾出现两个检测服务同时抢显存）。

失败场景已用 `--only` 参数补跑后合并，最终为 **19/19 全部成功**。
